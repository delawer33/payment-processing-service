# Повторы — через очередь с TTL и dead-letter обратно, DLQ после трёх попыток

Ошибка доставки webhook (таймаут, 5xx, отказ соединения) должна повториться с экспоненциальной
задержкой; после трёх попыток сообщение уходит в DLQ для ручного разбора. `nack(requeue=True)`
даёт мгновенный повтор без задержки и бесконечный цикл; `asyncio.sleep` внутри обработчика
держит prefetch-слот и теряет попытки при перезапуске процесса.

Решение — топология из трёх очередей на одном direct-обменнике `payments`:

| Очередь | Назначение | Аргументы |
|---|---|---|
| `payments.new` | рабочая, читает consumer | `x-dead-letter-exchange=payments`, `x-dead-letter-routing-key=payments.dlq` |
| `payments.retry` | ожидание перед повтором, читателей нет | `x-dead-letter-exchange=payments`, `x-dead-letter-routing-key=payments.new` |
| `payments.dlq` | окончательно упавшие, читателей нет | — |

При ошибке обработчик читает заголовок `x-attempt` (0 по умолчанию): если `attempt + 1 < 3`,
публикует копию в `payments.retry` с `expiration = base * 2^attempt` (1 с, 2 с, 4 с) и
`x-attempt + 1`, затем ack оригинала. По истечении TTL RabbitMQ сам перекладывает сообщение в
`payments.new`. Если попытки исчерпаны — `reject(requeue=False)`, и DLX очереди `payments.new`
кладёт сообщение в `payments.dlq` с заголовками `x-death`. Тот же DLX ловит и любой неожиданный
reject, так что потерять сообщение нельзя.

Альтернатива — плагин `rabbitmq_delayed_message_exchange`: даёт точные задержки, но его нет в
стандартном образе. Известное ограничение выбранной схемы: TTL проверяется у головы очереди, и
сообщение с большой задержкой задерживает за собой сообщения с меньшей. При трёх ступенях и
секундных задержках это несущественно; при большем разбросе — по очереди на ступень.

## Consequences

- Счётчик попыток живёт в сообщении, а не в БД: перезапуск consumer'а его не сбрасывает.
- Статус платежа при ретраях не меняется (ADR 0003): повторяется только webhook.
- Разбор DLQ — ручной; автоматического replay нет.
