# Идемпотентность создания платежа обеспечивает UNIQUE-ограничение, а не проверка в коде

Клиент может повторить `POST /api/v1/payments` (сетевой таймаут, ретрай на его стороне, два
инстанса клиента). Два платежа на одну сумму — прямой финансовый ущерб. Проверка «SELECT по
ключу, затем INSERT» в коде проигрывает гонку между двумя параллельными запросами.

Решение: `payments.idempotency_key UNIQUE NOT NULL`; вставка делается одним
`INSERT ... ON CONFLICT (idempotency_key) DO NOTHING RETURNING *`. Вернулась строка — платёж
новый, в той же транзакции пишется outbox. Не вернулась — читаем существующий платёж и сравниваем
`request_hash` (SHA-256 канонизированного тела). Совпал — отдаём `202` с тем же `payment_id`:
клиент не отличает повтор от первого запроса, что и требуется. Не совпал — `409 Conflict`: один
ключ пытаются использовать для двух разных платежей, и это ошибка клиента, а не повтор.

Альтернатива — отдельная таблица idempotency-ключей с TTL, как у Stripe. Она нужна, когда ключ
защищает разные эндпоинты или ответы хранятся целиком. Здесь ключ принадлежит ровно одной
сущности, и колонка в `payments` проще и строже.

## Consequences

- Ключ глобален, не per-client: два клиента с одним ключом получат один платёж. Для многопользовательского
  API ключ стал бы составным `(client_id, idempotency_key)`.
- Ключи не истекают; таблица растёт вместе с платежами, что для платежей нормально.
- Повтор с тем же ключом не публикует второе событие: outbox пишется только в ветке «вставилось».
