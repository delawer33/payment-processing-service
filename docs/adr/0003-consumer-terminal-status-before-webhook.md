# Consumer фиксирует итоговый статус до отправки webhook, а повторная доставка никогда не вызывает шлюз снова

Consumer делает три шага: шлюз (2–5 с, 10 % отказов), запись статуса, webhook. Сообщения из
RabbitMQ приходят at-least-once (ADR 0001, nack, обрыв соединения после обработки). Наивный
обработчик «шлюз → статус → webhook, при любой ошибке nack» при неудачном webhook повторит
вызов шлюза: второе списание, а с вероятностью 10 % ещё и перезапись `succeeded` на `failed`.
Это и есть главный риск сервиса.

Решение: обработка идёт под `SELECT ... FOR UPDATE` по строке платежа. Если статус уже не
`pending`, шлюз не вызывается вовсе; остаётся только недоставленный webhook. Если `pending` —
вызов шлюза, и его результат (`succeeded`/`failed`, `processed_at`) коммитится немедленно,
отдельной транзакцией, раньше любой попытки отправить webhook. Webhook — второй шаг со своим
признаком `webhook_delivered_at`; его ошибка ведёт в retry (ADR 0004), который снова попадёт в
ветку «статус терминальный, только webhook». Отказ шлюза — это бизнес-исход `failed`, а не
ошибка обработки: он не ретраится. Переход из терминального статуса запрещён триггером в БД, а
не проверкой в коде: будущий код не сможет его нарушить.

Блокировка строки держится на время вызова шлюза (до 5 с). Это сознательно: параллельный дубль
того же `payment_id` дождётся и увидит терминальный статус, вместо того чтобы вызывать шлюз
параллельно. Альтернатива — промежуточный статус `processing` с короткими транзакциями — требует
статуса, которого нет в контракте, и отдельного механизма «подвисших» платежей.

## Consequences

- Обработчик идемпотентен по `payment_id` при любом числе доставок и параллельных consumer'ов.
- Соединение с БД занято на время вызова шлюза; prefetch consumer'а ограничивает их число.
- Реальный шлюз получал бы `payment_id` как собственный idempotency key — его таймаут всё ещё
  не означает отказ. Эмуляция таймаутов не имеет; это оставлено за рамками.
