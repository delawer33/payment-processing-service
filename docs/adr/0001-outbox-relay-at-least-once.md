# Событие о платеже пишется в outbox той же транзакцией, relay публикует его at-least-once

API создаёт платёж и должен сообщить об этом consumer'у через RabbitMQ. Публиковать из обработчика
запроса напрямую нельзя: если брокер недоступен или процесс упал между `COMMIT` и `publish`,
платёж останется `pending` навсегда. Обратный порядок (сначала publish, потом commit) теряет
платёж, если упала БД. Нужна атомарность «запись + событие», которой у двух разных систем нет.

Решение: таблица `outbox` в той же БД; `INSERT` в `payments` и `INSERT` в `outbox` идут одной
транзакцией. Отдельный цикл (relay) в процессе consumer раз в `OUTBOX_POLL_INTERVAL` забирает
пачку `WHERE published_at IS NULL ... FOR UPDATE SKIP LOCKED`, публикует с publisher confirms и
только после подтверждения брокера ставит `published_at`. Если процесс упал между publish и
`UPDATE`, событие уйдёт второй раз — поэтому гарантия at-least-once, а дедупликация лежит на
consumer (ADR 0003). Relay живёт в процессе consumer, а не API: у consumer уже есть соединение с
брокером, а API остаётся без зависимости от RabbitMQ и его падение не мешает приёму платежей.

Альтернатива — Debezium/логическая репликация WAL: честнее, но это отдельная инфраструктура ради
одной таблицы. Polling с `SKIP LOCKED` безопасен при нескольких репликах consumer и достаточен для
нагрузки сервиса.

## Consequences

- Платёж и событие нельзя разнести по разным транзакциям; сервисный слой принимает одну сессию.
- Consumer обязан быть идемпотентным по `payment_id`: одно и то же событие может прийти дважды.
- Частичный индекс `outbox (id) WHERE published_at IS NULL` обязателен: relay читает только хвост.
- Задержка между созданием и обработкой ≥ интервал опроса (по умолчанию 0.5 с).
